# Seating layout database setup

This is the SQL to run on the API's PostgreSQL database for shared layout persistence. It keeps:

- Real guest tables in the existing `wedding.seating_table` table, with positions in `wedding.seating_layout_position`.
- The layout-only Main Table in its existing singleton table.
- Additional generic, unassigned layout tables in `wedding.seating_layout_generic_table`. These are not seating tables and cannot receive guest assignments.

## Run the setup

Connect to the same database used by the API (from the repository root):

```sh
psql "$DATABASE_URL"
```

Paste and run this SQL in the `psql` prompt:

```sql
BEGIN;

CREATE SCHEMA IF NOT EXISTS wedding;

CREATE TABLE IF NOT EXISTS wedding.seating_layout_position (
  table_id INTEGER PRIMARY KEY
    REFERENCES wedding.seating_table (table_id)
    ON DELETE CASCADE,
  x DOUBLE PRECISION NOT NULL CHECK (x >= 0 AND x <= 1),
  y DOUBLE PRECISION NOT NULL CHECK (y >= 0 AND y <= 1)
);

CREATE TABLE IF NOT EXISTS wedding.seating_layout_main_table (
  singleton_id BOOLEAN PRIMARY KEY DEFAULT TRUE CHECK (singleton_id = TRUE),
  x NUMERIC NOT NULL CHECK (x >= 0 AND x <= 1),
  y NUMERIC NOT NULL CHECK (y >= 0 AND y <= 1),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS wedding.seating_layout_generic_table (
  generic_table_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  table_name TEXT NOT NULL,
  capacity INTEGER NOT NULL DEFAULT 0 CHECK (capacity >= 0),
  notes TEXT,
  x NUMERIC NOT NULL CHECK (x >= 0 AND x <= 1),
  y NUMERIC NOT NULL CHECK (y >= 0 AND y <= 1),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

COMMIT;
```

The script is safe to run again. It creates storage only; it does not add fake rows to `wedding.seating_table` or make changes to existing guest assignments.

## Verify the tables

Run:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'wedding'
  AND table_name IN (
    'seating_layout_position',
    'seating_layout_main_table',
    'seating_layout_generic_table'
  )
ORDER BY table_name;
```

The query should return all three names. An empty `seating_layout_main_table` means the frontend should use its default center position. Generic tables are added later through the API and remain outside guest seating/assignment data.

## Application behavior still required

These database tables provide storage; the API still needs endpoints and layout loading/saving for generic tables. Those API operations should read/write `seating_layout_generic_table` and must not insert generic records into `wedding.seating_table` or `wedding.seating_assignment`.

The database schema alone does not enforce the rule that a real seating table with assigned guests cannot be edited or deleted. The API must check for assignments before changing/deleting a real table and reject the operation when assignments exist. Moving a real table's canvas position remains allowed. Generic layout-only tables have no assignment records, so they can be added, edited, and deleted independently.
